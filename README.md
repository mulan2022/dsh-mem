# dsh-mem

基于 **markdown vault** 的 DeepSeek Harness 记忆空间插件。

设计文档：[`docs/DESIGN-memory-plugin.md`](docs/DESIGN-memory-plugin.md)

## 核心理念

**markdown 文件是唯一事实源，SQLite 只是可随时重建的派生索引。**

记忆是长期资产 —— 可手改、可 git、可备份，不该锁在二进制库里。
任何时候删掉 `index.db` 都不丢数据。

## 空间模型

**只有三样东西**，与 UI 的三个 tab 一一对应：

```
<dsh home>/.dsh-mem/
├─ index.db                派生索引（可删）
├─ workspaces.yaml         工作区类型登记表（这个目录算聊天还是项目）
├─ shared/                 【常驻记忆 + 全局共用】← 主动注入
│   ├─ instructions.md       常驻记忆（上限 50，不参与自动淘汰）
│   └─ sections/             身份 / AI 设定 / 准则 / 能力画像 / 项目偏好 / 技术栈
└─ spaces/
    ├─ chat/               【聊天记忆】
    └─ project/            【项目记忆】一个 tab，不随项目数增长
        └─ projects/
            └─ MemoryChat/     每个项目一个目录（以项目名命名）
                ├─ sections/   项目目标 / 待办 / 架构 / 决策 / 踩坑
                ├─ timeline.md 项目时间线
                └─ entities/   这个项目内部的模块、依赖、协作者
```

**注入规则**：

| | 主动注入？ |
| --- | --- |
| 常驻记忆 + 全局共用（身份 / 准则 / 能力画像 / taste） | ✅ 每次都注入 |
| 聊天记忆（聊天会话） | ✅ |
| **项目记忆（包括当前项目）** | ❌ **一律不注入** —— AI 自己调工具取 |

项目会话只给**一行轻量指针**（"你在项目 X 里，它的记忆不在你的上下文里，
用 `mem_search` / `mem_entity` / `mem_diff` 取"）。

**为什么**：项目细节量大、而且多数时候用不上；全塞进上下文既贵又吵。
开局给标题、需要时再去翻，是这套设计一贯的做法。

**为什么项目不各占一个 tab**：项目数会长，tab 数不该跟着长。
所有项目是「项目记忆」里 `projects/` 下的子目录，在右侧文件树点进去。

**为什么能力画像在全局层**：它们跨项目、不属于任何具体项目。
曾经放在 `project/_shared/`（跨项目层），那导致**聊天会话读不到它们**，已合并。

**为什么聊天和项目分开**：两边记的东西不一样（价值观/态度/沟通风格 vs
目标/架构/决策/时间线），各有自己的 `sections.yaml`。

## 三层置信度

```
raw/                原始素材 + raw/anchors.jsonl（来源锚点表）
  ↓
observations.md     暂存：信号弱、未确证 —— 不常驻、不进 README
  ↓ dream 确证
sections/ entities/ 确证：参与常驻注入
```

**每条 observation 都必须带来源锚点**（`[^N]` ↔ `raw/anchors.jsonl` 里的
`{session, turn, at}`）。锚点写不进去，正文就不写 —— 查不到出处的记忆不如不记。

锚点表**旁挂**而不内嵌，是为了让"晋升"这件事不可能出错：一条记忆从
`observations.md` 搬到 `sections/` 时，`[^12]` 跟着正文走，锚点表一动不动。

## 注入怎么工作

三条路径，频率各不相同：

| | 位置 | 时机 | 为什么 |
| --- | --- | --- | --- |
| **静态手册** | `systemPrompt.section()`（order 3000） | 注册一次 | 文本恒定 → 前缀稳定 → **KV 缓存友好** |
| **常驻记忆 + 常驻 section + 实体目录** | 独立的 plugin 消息，**插在真实用户消息之前** | 每会话一次；压缩后再注一次 | 顺序反了语义就崩；每轮都注会线性膨胀 token |
| **实体正文 + 顺链一跳** | 另一条独立的 plugin 消息，同样在用户消息之前 | **每条用户消息**都可能命中，按会话去重 | 与 A 层频率不同；同一实体页不重复塞 |

### 三档信息量（照搬"文献综述"的思路）

| 档 | 内容 | 成本 |
| --- | --- | --- |
| **开局全量** | 常驻记忆 + 常驻 section（压缩总览）+ **实体目录（只列名字 + kind/status）** | 固定开销 |
| **按需现查** | 实体**正文** —— 提到名字自动展开，或用 `mem_entity` 主动翻 | 用到才付 |
| **几乎不主动塞** | 原话、语气、某次聊岔的细节（来源锚点重访，P9） | 平时为零 |

**关键在于开局只给标题**：目录便宜、正文贵，这就是"看到引用再去翻原文"。

### 实体链接

正文里的 `[[实体名]]`：

- **UI**：渲染成可点击的蓝色链接，点了跳到那一页（`/dsh-mem/entities` 提供 name→path 映射，不靠猜文件名）
- **注入**：名字留在句子里，模型一眼看到有哪些可翻；顺链一跳的邻居只给名字，不展开正文

A 层内容 = `shared/` 层的常驻记忆 + 标记 `resident: true` 的 section。
实体检索目前只扫 `shared/` 与 `chat/` 两个 vault（v10 起跨项目层已并入 `shared/`）。
**已知缺口**：项目分区的实体页还进不了 `mem_entity` 的索引 —— 项目会话拿到的指针
文案里写着"可以用 `mem_entity` 翻实体页"，这条目前够不到。

### 实体检索为什么不需要向量

vault 是**文档**而不是一堆原子事实。人提到某个项目/概念时通常会说它的名字，
名字命中就是精确匹配 —— 不需要语义相似度去猜。向量只在"没说出实体名、
而是描述性提问"时才需要（P8，且默认关）。

匹配用子串（中文没有词边界），限制最小长度压低误命中，多个命中按名字长度降序
（长名更具体）。**顺链只跳一跳** —— 否则"提到攀岩就摸到高斯泼溅、再摸到…"
会一路扩散，把上下文吃光。

## 聊天空间：RCC（最近 40 场的用户原话）

**只挂聊天空间**。项目空间已经有"时间线摘要常驻 + 详情按需取"，再挂一套就是
同一个问题两个答案。聊天记忆是散的态度/生活/情绪，**没有天然结构**，
靠"最近说过什么"兜底比靠检索准。

RCC = 最近 N 场（默认 **40**，计数单位是**场**不是消息）里**用户的全部发言**，
逐字引用、不加摘要、不做检索；场与场、句与句之间用 `||||` 分隔，
每场带一行"场号 + 时间 + 标题"。**只保留用户的，不保留 AI 的**。

| 层 | 裁什么 | 默认 |
| --- | --- | --- |
| 整场 | 一场只留**前面 12 句**，后面全砍 | `rccHeadTurns` 12 / `rccTailTurns` 0 |
| 单条 | 一条发言太长就掐中段（头 60 字 + 尾 40 字） | `rccHeadChars` 60 / `rccTailChars` 40 |
| 总量 | 整块超预算就从**最旧**的场开始丢（安全网，正常不该触发） | `rccMaxChars` 40000 |

两层裁剪都只留一个光秃秃的 **`[TL;DR]`** 标记 —— 不写"此处省略 N 字/句"：
**省了多少是我们自己算得出来的**，每次注入都带上纯属白花 token。

### 补丁：砍掉的部分能补回来

每轮之前拿本轮用户消息在 `turns.user_text` 上做 BM25，命中**且那一轮真的被砍掉**
（两层都要看：落在被砍的句段里，或那条发言自己超了 100 字），就把
**那一轮**的完整原话追加一条 —— 不重发 RCC、不动别的场、**也不整场端上来**
（用户拍板：「不是补整场对话啊，是触发关键词的那一个对话」）。

两道闸门：

| 闸门 | 规则 | 为什么 |
| --- | --- | --- |
| **辨识度** | query 里得有**有辨识度的词**命中（`rcc` 4.5% 算，`记忆` 24.7% / `这个` 35% 不算，门槛 = `df≥3 且 df/n≥10%`） | 一句「宝宝你有记忆了吗」曾靠 `记忆` 一个泛词把两整场 4481 字符拉进上下文 |
| **看不见** | 命中的那一轮在 RCC 里确实被 `[TL;DR]` 遮住了 | 看得见的已经完整在上下文里，再补一遍是白花预算 |

**成本上界**：每轮最多 `rccPatchK`（默认 **1**）段 × 一轮原话的长度；
同一**轮**在一个会话里只补一次。实测同一句话：改动前 2 段 / 4481 字符 → 改动后 **1 段 / 121 字符**。

### 分叉会话会被折叠

DSH **不删会话日志**（界面上删了、磁盘上还在），手滑点出来的分叉会话用户发言
往往是父会话的**前缀**。RCC 拼装前先折叠这种被包含的分支 —— 否则一场分叉就白占
一个名额（用户原话：「那个是我不小心点到了分叉会话，结果删了都还有记录，
这种要不当成一场？不然很占名额哎」）。

### 成本

**聊天会话的上下文注入 15–20k token 可以接受**。参照：Kimi 那边光上下文注入
就要 40k 左右，能保留 40 场靠的正是"整场只留 12 句"这套截断 —— 差别在于
**它砍掉就没了，我们砍掉的部分有补丁能补回来**。

## 自动写入怎么工作（P4）

> **v11 起这条链被大幅收窄**：用户拍板「**不要在对话过程中频繁改动 memory**，
> 这个工具除非用户要求改或者记忆跟之前的有冲突才能碰，**不然都由 dream agent 完成**」。

挂 `agent/turn-stopping`，只做两件事，**都不调模型、都不 steer 之外的动作**：

| | 做什么 |
| --- | --- |
| **「用户要求记住」的提醒** | 只在用户**明说**「记住 X」时 steer 一条 `[mem-reflect]`，提醒落库 |
| **原始轮次采集** | 把每轮对话原文追加进 `<home>/.dsh-mem/raw/turns/<会话>.jsonl`，**给 dream 读** |

原始轮次落在 **`shared/` 与 `spaces/` 之外**（`raw/` 是"还没判归属"的素材池）——
因为**归属由 agent 按内容判断**：项目目录里的闲聊该进聊天记忆，
而按 cwd 预分就等于替它判完了。dream 时**每个会话派两个 agent**
（一个闲聊、一个项目）各读同一份素材、各捞各的。

**轮次级触发已删除**：以前"连续工具调用 ≥5"或"每 3 轮"也会提醒记东西 ——
那正是"在对话过程中频繁改记忆"的来源。现在**判断推迟到晚上做**，
而素材由上面第二行保住（不然 dream 晚上无米下锅）。

工具侧也把前提写死了：`mem_observe` 的说明第一句就是「**不要在对话过程中主动记东西**，
只有**用户明确要求**、或**与已有记忆冲突**时才调用」。

开关：`autoWrite`（提醒）/ `captureTurns`（采集）。

### 写入落点由代码决定，不由调用方决定

`mem_observe` **没有**"写去哪个空间"这个参数。落点由当前会话的 cwd 硬推导：
向上找到项目根标记（默认 `.git`）→ 写该仓库的分区；找不到 → 写聊天空间。
调用方没有机会写错地方 —— 隔离由结构保证，不靠"记得过滤"。

（登记表与"未登记工作区首次进入时询问"已随 P4.6 落地；v10 之后又叠了一层
「agent preset 优先」的判定，见下节。）

## 项目时间线怎么工作（P4.5）

```
tools/result（write/edit 已经附好 meta.diffs）
   │ 按会话缓冲
   ▼  轮次结束时聚合
timeline.md          摘要（resident → 常驻注入）：一轮一行 + [→id]
   │ [→ id]
raw/timeline/<id>.md 详情（永不主动注入）：完整的改前 / 改后
```

**diff 不用自己算**：`write`/`edit` 本来就把 `meta.diffs` 附在结果上，
所以这里省掉了"自己 diff / 做文件快照"整块工作。

**一轮一行，不是一改一行**：摘要会被常驻注入，按 tool call 记的话，
一场重构能写下几十行，直接把上下文预算吃光 —— 那就违背了设计前提。

**详情按需取**：`mem_diff` 就是那道"第二层"的门。只有当模型自己判断
某个历史改动还影响现在时才开。三种失败都给具体原因，不猜也不编：
指针号不存在（会列出现有的）/ 该锚点是观察类、没有详情文件 / 锚点在但详情被清理了。

**已知边界**：只采集带 diff 的工具结果，外加 write/edit/move/delete 这类**改动类工具**
的调用记录。**命令行（shell）间接改的文件不会被采集** —— 收进来会让时间线
变成命令流水账，得不偿失。

时间线的落点规则与 `mem_observe` **故意不同**：它落到 cwd 对应的项目分区
（没有仓库标记时按目录本身分区），而不是聊天空间 —— 因为"这是哪个目录里的改动"
这个问题总是有答案，而"这是关于谁的事实"不一定有。

## 空间与注入规则（P4.6 + agent preset 判定）

**一个工作目录的记忆进哪个空间**，判定顺序是：

```
agent preset（id === 'chat' → 聊天空间）
  →  登记表（workspaces.yaml）
  →  仓库标记（默认 .git）
  →  default（ask / chat / project）
```

**preset 是用户声明的意图，压过登记表与仓库标记** —— 只有读不到 preset（服务未就绪、
投影为空）时才退回下面那条链。除 `chat` 之外的任何 preset 一律走项目空间，分区仍按
cwd 推导。"聊天模式"preset 已建好（`~/.dsh/.agent-presets/chat/`）。

登记表可以手改，也可以让 AI 用 `mem_space` 登记（只在用户明确表态时）。
登记某个目录，它的**所有子目录**都算在内。`ask` 时未登记的工作区会在会话里问一次，
问过就记进 `state.json`，不再反复打扰；在用户回答之前按**聊天空间**兜底
—— 那是破坏性最小的选择。

**注入哪些、不注入哪些**（这是整个设计里最重要的行为差异）：

| 空间 | 注入策略 |
| --- | --- |
| 共享层（常驻记忆 + 全局共用 section） | ✅ 每次都注入 |
| **聊天空间**（当前会话是聊天时） | ✅ 常驻 section + 实体目录 + RCC |
| **项目记忆（含当前项目、含其它分区）** | ❌ **一律不注入正文** |

**项目会话只给一行轻量指针**（"你在项目 X 里，它的记忆不在你的上下文里，用
`mem_search` / `mem_entity` / `mem_diff` 取"）；**其它项目**再多给一行规模
（"它有 12 条记忆、3 条时间线"）。正文一律由 AI 主动 `mem_search` 取。

> **v10 之前这张表是反的**：跨项目层 `_shared` 与「当前分区」都标 ✅。v10 把跨项目层
> 并进了共享层，并把**项目记忆整体**从注入里拿掉了 —— 项目细节量大、多数时候用不上。

### 跨项目检索为什么不是 N 个库

因为入口 2 必须能一次搜遍所有项目。所以项目空间是"**单例根 + 硬隔离分区**"，
而不是 N 个独立库 —— 检索在派生索引里一次查完，结果带归属标注。

检索用 **CJK bigram + Unicode 整词**分词（中文没有词边界，这是绕开 FTS5
把整串中文当一个 token 的实测结论），打分是"词频饱和 × 查询覆盖率 × 长度惩罚 + 名字加成"。
**这是第一版够用的量级，不是调过的** —— 等 P-1 的检索测评集做出来再拿数据调。

### 分区元信息跟着分区走

每个项目分区自带 `meta.yaml`（key / path / name / 时间戳），而不是在 mem 根下维护一份
中心化的 `projects.yaml`。分区被搬走、备份、复制时元信息跟着走，也不会出现
"注册表说有这个项目、目录却不在了"这种两边对不上的状态。
