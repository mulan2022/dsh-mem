## 1. 铁律（不可违反）

> **任何一轮对话都不允许被静默丢弃。**

出 40 条窗口的轮次必须已完成二者之一：
(a) 已落进 `raw/` 或 `observations.md`；(b) 已被压缩记录覆盖。

实现：轮次出窗口前做覆盖检查，未覆盖则**先落 raw 再删**，
失败则**保留该轮并告警**（宁可窗口临时超 40，也不许失忆）。

## 2. 双分层（常驻记忆 / 自动沉淀）

| 层 | 名称 | 来源 | 注入 | 淘汰 | 上限 |
|---|---|---|---|---|---|
| **A** | **常驻记忆** | 用户明确要求记住的 | **永久常驻，始终遵循** | **不参与 dream 淘汰** | 50 条 |
| **B** | 自动沉淀 | 提炼轮 + dream | 参与检索 | 参与晋升/降级/归档 | 无硬上限 |

**存储**：`<home>/.dsh-mem/shared/instructions.md`，每条一行 `- 内容`。
放**共享层**而不是某个空间里，因为它两个空间都要生效。

**写入路径：只有 AI 工具，没有别的入口。** 模型用 `mem_remember` / `mem_forget`
两个工具增删（工具名刻意与参考实现的 `memory_remember` 错开，避免同时装两个记忆插件时冲突）：

- **没有 HTTP 写接口** —— UI 那侧只有 `GET /dsh-mem/instructions` 读列表
- **不供人手动编辑** —— 文件头写明由工具维护，手工改动会被下次工具写入覆盖
- **只在用户明确要求时调用**（"记住 X" / "忘掉 X"），写进了工具的 description

把写入口收敛成工具、读接口留成只读，这条约束就由**结构**保证，
而不是靠"约定别乱写" —— 与 §4.2「隔离靠硬代码」是同一条原则。

**上限行为**：满 50 条时**拒绝新增并返回明确原因**（`ok:false` + 说明），
绝不静默淘汰最旧的 —— 静默淘汰等于变相失忆，与 §1 铁律冲突。

> **命名说明**：这一层**不叫「记忆指令」**。Kimi 用"记忆指令"，我们叫**常驻记忆** ——
> 它描述的是**机制**（常驻注入、始终在上下文里），而不是"用户下达指令"这个动作。
> 而且它接得上本项目已有的术语（§4.2.4 的"常驻"注入）。

## 3. 三层置信度（v4 新增，[Kimi参考]）

Kimi 的 `observations.md` 首页写着：

> *"Provisional scratchpad. Signals not yet strong enough to enter sections/entities
> live here. Promoted by future dreams when corroborated. Not included in README.md."*

照搬这个**置信度分层**：

```
raw/                    原始素材（未加工：轮次摘录、来源锚点）
   │ dream 提炼
   ▼
observations.md         暂存区：信号弱、单次出现、未确证
   │ 后续 dream 发现被 corroborate（再次出现/与已有记忆一致）
   ▼                     未确证则随 observ 过期清理
sections/ + entities/   确证区：进入 index.md 与 README.md，参与常驻注入
```

**关键规则**：`observations.md` 的内容**不注入 README、不常驻**，只在相关检索命中时被读到。
这条防止"一次性的随口一提"污染长期画像。

## 4. Vault 结构（唯一事实源）

```
<home>/.dsh-mem/vault/            ← 全局层：soul / user / 全局 rules
<workspace>/.dsh-mem/vault/       ← 项目层

├─ README.md         合成后的主上下文（Personal Context / Work Context / This Month …）
│                    每条断言带【角标引用】指向来源锚点
├─ index.md          自动生成：Sections 列表 + Entities 列表
│                    文件头注明 "Generated from canonical vault files.
│                    Relationships are maintained in markdown links and indexed by write tools."
├─ observations.md   暂存区（§3），按日期分组
├─ log.md            dream 审计日志（§5.6）
├─ sections.yaml     section 定义（名称/顺序/是否常驻）
├─ sections/         各 section 正文
├─ entities/         实体页：人 / 项目 / 概念 / 地点 / AI 自身
└─ raw/             原始素材
   └─ anchors.jsonl 来源锚点表（旁挂：正文带 [^N]，锚点表按 id 查）
```

**为什么改成文件而不是 SQLite**（这是 v3 → v4 最大的改动）：

1. **用户要求"记忆空间在 DSH 里展示"** —— 文件树 + markdown 渲染是天然形态，
   数据库要在 UI 里重建一套视图，且用户无法直接编辑
2. **可手改、可 git、可备份** —— 记忆是长期资产，纯二进制库一旦损坏就没了
3. **与设计意图一致** —— 我们要做的是"wiki 式记忆"，wiki 的本质是文件

**代价（必须承认）**：检索比 SQLite 慢、并发写要加锁、需要维护派生索引。
缓解见 §5.2。

### 4.1 SQLite 的定位（派生索引，非事实源）

```sql
-- 可由 vault 文件完整重建（rebuild 命令）
CREATE TABLE idx_entries (
  path        TEXT PRIMARY KEY,   -- vault 内相对路径
  kind        TEXT NOT NULL,      -- section | entity | observ | instruction
  name        TEXT,               -- 实体名/section 名（精确命中入口）
  status      TEXT,               -- active|ongoing|stuck|abandoned|done
  body        TEXT NOT NULL,      -- 全文，供 BM25
  keywords    TEXT,
  importance  INTEGER,
  embedding   BLOB,               -- Float32Array，可选
  mtime       INTEGER NOT NULL,   -- 增量重建用
  updated_at  INTEGER NOT NULL
);
CREATE TABLE idx_links (from_path TEXT, to_path TEXT, relation TEXT, PRIMARY KEY (from_path, to_path));
CREATE TABLE anchors   (id TEXT PRIMARY KEY, owner_path TEXT, session_id TEXT, turn_seq INTEGER, created_at INTEGER);
CREATE TABLE turns     (id INTEGER PRIMARY KEY AUTOINCREMENT, session_id TEXT, project TEXT,
                        turn_seq INTEGER, user_text TEXT, ai_compact TEXT,
                        covered_by TEXT, created_at INTEGER);
-- 对话（场）级：RCC 的编排单位与截断状态（§5.8）。标题来自 dsh-session-title。
CREATE TABLE sessions  (session_id TEXT PRIMARY KEY, title TEXT, started_at INTEGER,
                        in_rcc INTEGER DEFAULT 0, rcc_truncated INTEGER DEFAULT 0);
CREATE TABLE seen      (session_id TEXT, path TEXT, seen_at INTEGER, PRIMARY KEY (session_id, path));
CREATE TABLE windows   (session_id TEXT PRIMARY KEY, project TEXT, last_seen INTEGER,
                        dream_skip INTEGER DEFAULT 0, lease_until INTEGER, last_dream_at INTEGER);
```

**删除原则**：任何时候删掉 `index.db` 都不丢数据 —— 它是纯派生。
文件侧若有 `mtime` 变化，下次启动增量重建对应条目。

## 4.2 双空间模型（D7）

**需求原话**：「做项目/聊天分开给记忆空间要整理的东西，然后每次添加项目文件夹的时候
选择是聊天还是项目」。**随后修正**：「项目也做成单例全局的，只不过跟聊天记住的东西不一样，
项目里 observation 可以记用户代码水平、数学水平、项目偏好之类的东西为主，
聊天里的就是价值观人生观态度之类的……项目这边各种时间改了什么代码要记得更多，总结成项目时间线」。

### 4.2.1 DSH 侧能力核实结果（本机查证，非推测）

| 事实 | 结论 |
|---|---|
| `sidebar.workspaces` 的 kind | `single`，owner 是工作区浏览器组件 |
| 有没有工作区**行级**子槽 | **没有**（唯一子槽是 `.directoryFlow`）→ 无法在行上加类型徽章 |
| 有没有可插入的「添加工作区」交互洞 | **有**：`sidebar.workspaces.directoryFlow` 与 `conversation.hero.workspace.directoryFlow`，插件**可占用** |
| 占用方拿到什么 | `createWorkspace({ path })` 回调 |
| 占用的代价 | **会替换掉原本的 picker**（native OS 选择器 / browse 对话框），选目录交互要自己实现 |
| 有没有原生「项目时间线」能力 | **没有**。相关的只有 deliverables（每轮产出文件）与 checkpoint-policy，都不是时间线 |
| 有没有可接的改动观测钩子 | **有**：`tools/result` 事件（emit，给 `exec` + `result`），官方 `dsh-agent-instructions` 已用它观察 first-party `read`/`write`/`edit` |

### 4.2.2 类型选择入口

| 入口 | 可行性 | 代价 | 选用 |
|---|---|---|---|
| ① 占用 `directoryFlow` 洞 | ✅ 可占用 | 夺走原生选择器，需自实现选目录 | ❌ 暂不用 |
| ② **采用后补一步** | ✅ 一定能做 | 原生选择器照常，选完弹类型选择 | ✅ **默认入口** |
| ③ 记忆空间 UI 里登记 | ✅ 一定能做 | 用户手动登记，不拦截 | ✅ 兜底 + 批量管理 |

**决定：② + ③。** 不做①——为加一个下拉框而夺走用户熟悉的原生目录选择器，收益不抵代价。

### 4.2.3 空间布局：聊天单例 + 项目**硬隔离分区**

**用户修正**：「落进同一个 vault 的问题当然得靠硬代码解决啊，不同的项目文件夹自己单开一个，
而且其它项目的记忆不主动注入上下文，只有提到了、AI 主动查看的时候才注入，
但是聊天就随便，一直都是全局主动注入上下文的」。

```
<home>/.dsh-mem/
├─ shared/                    【全局层】所有会话都注入
│   ├─ instructions.md        常驻记忆（上限 50，不参与自动淘汰）
│   └─ sections/             用户身份 / AI 设定 / 全局准则 /
│                            能力画像 / 项目偏好 / 技术栈偏好
└─ spaces/
    ├─ chat/                  【聊天记忆·单例】只在聊天会话注入
    │   ├─ README.md  index.md  observations.md  log.md  sections.yaml
    │   ├─ sections/          价值观与人生观 / 态度与倾向 / 沟通风格 / 品味偏好 / 关系 / 本月状态
    │   ├─ entities/          人 / 关系 / 兴趣 / 概念 / 事件
    │   └─ raw/
    └─ project/proj/
        ├─ d--demo-MemoryChat/    ← 每个项目文件夹一个独立分区【项目记忆】
        │   ├─ README.md  index.md  observations.md  log.md  sections.yaml  meta.yaml
        │   ├─ sections/   项目目标 / 架构 / 决策与教训 / 待办
        │   ├─ entities/   模块 / 外部依赖 / 协作者
        │   ├─ timeline.md 项目时间线
        │   └─ raw/
        └─ d--work-myproj/        ← 同上
└─ workspaces.yaml            工作区类型登记表（这个目录算聊天还是项目）
```

> **v9 修订（实测后收敛）**：原设计有四个抽屉 —— `shared`（共享身份层）、
> `spaces/chat`、`project/_shared`（跨项目层）、`project/proj/<key>`。
> 其中 `shared` 与 `project/_shared` **没有任何行为差别**：两个都是"关于你、
> 不属于任何具体项目"的东西，注入范围也几乎一样。分成两个抽屉只多一次点击，
> 还导致**聊天会话读不到能力画像**（它被关在项目空间里）。
> 现已合并为**一个全局层**。模型收敛成"**一个全局层 + 一个上下文层**"：
> 会话要么是聊天、要么在某个项目里，每次注入的都只是「全局层 + 当前那一个」。

> **v10 修订（用户拍板后）**：`工作区` 不该是一个 tab，项目也不该各占一个 tab。
> 用户原话：「**这里总共应该只有三个东西，常驻记忆，聊天记忆，项目记忆**；
> 项目记忆里可以把 entities 改成 projects，这个 MemoryChat 相关的记忆应该放在 projects 下面；
> 而 readme 啊能力啊 taste 啊是全局共用的，平时上下文只主动注入这些东西，
> **project 里具体的东西需要 AI 自己去调用**」。
>
> 三处改动：
> 1. **tab 收敛为 3 个**：常驻记忆 / 聊天记忆 / 项目记忆。项目不再是 `spaces/project/proj/<key>/`
>    各自一个 tab，而是**一个**项目记忆空间里 `projects/<项目名>/` 的子目录 ——
>    **tab 数不随项目数增长**。
> 2. **注入规则变了**：项目记忆（**包括当前项目**）**一律不主动注入**，只给一行轻量指针，
>    正文由 AI 调 `mem_search` / `mem_entity` / `mem_diff` 取。
>    （这推翻了 §4.2.4 里"当前项目分区 ✅ 主动注入"那一行。）
> 3. **`工作区` 从设置导航里去掉**，收进「项目记忆」页底部的一个折叠块 ——
>    它决定"哪些目录算项目"，与那一页贴题。
>
> 目录名也从分区 key（`d--demo-MemoryChat`）改成**人类可读的项目名**（`MemoryChat`），
> 便于在文件管理器里一眼认出。旧目录由 `migrateLegacyProjectDirs` 自动搬家
> （纯位置移动，数据一字不改）。

```yaml
# <home>/.dsh-mem/workspaces.yaml
spaces:
  "D:\\demo\\MemoryChat": project
  "D:\\chat":             chat
default: ask        # ask | chat | project（未登记工作区的兜底行为）
```

**关键点**：项目空间仍是"**单例根**"（一个索引、一次备份、可跨项目检索），
但**内部按项目文件夹硬隔离** —— 隔离由代码强制（写入口只认当前分区），不是靠约定。

**分区 key 怎么算（硬代码）**：

```
cwd → 向上找 projectRootMarkers（默认 ['.git']）→ 命中则用该目录
    → 未命中则用 cwd
    → 规范化（小写盘符、统一 /、解析符号链接）
    → 转成目录名：D--demo-MemoryChat
    → 记进 proj/ 目录名 与 projects.yaml 的映射
```

`projectRootMarkers` 沿用 `dsh-agent-instructions` 的默认 `['.git']` —— **一个仓库 = 一个项目**。
在仓库子目录里开会话，归到仓库根的分区，**不会因为换个子目录就换记忆**。

### 4.2.4 注入规则（本方案的核心行为差异）

| 空间 / 分区 | 注入策略 |
|---|---|
| **全局层 `shared/`** | ✅ **每次都注入** —— 常驻记忆 + 驻留 section（身份/准则/能力画像/项目偏好） |
| **chat** | ✅ 主动注入，不过滤（价值观、态度、沟通风格） |
| **project / 当前项目分区** | ✅ 主动注入（项目目标、待办、时间线） |
| **project / 其它项目分区** | ❌ **不主动注入** |

> v9 起 `project/_shared` 已并入全局层，上表不再有它。

其它项目的记忆只有两个入口：

1. **被提到时** → 注入**轻量指针**，不注入正文。
   例如用户提到 `MemoryChat`，注入：
   `你提到了项目 MemoryChat，它有 12 条记忆与 3 条时间线记录，可用 memory_search 查看。`
   **让 AI 自己决定要不要看**，而不是把别的项目正文塞进上下文。
2. **AI 主动查看** → `memory_search` **允许跨项目检索**，返回结果带项目归属标注。

**为什么跨项目检索必须可用**：入口 1 只给指针，入口 2 才是真取用。
若物理上拆成 N 个独立库，跨项目检索就得逐个打开数据库 ——
所以选"**单例根 + 硬隔离分区**"，而不是 N 个库。

### 4.2.5 两套模板（"记住的东西不一样"的落点）

| | **聊天空间** | **项目空间** |
|---|---|---|
| sections | 价值观与人生观、态度与倾向、沟通风格、品味偏好、关系、本月状态 | **能力画像**、**项目偏好**、技术栈、**项目时间线**、决策与教训、待办 |
| entities | 人、关系、兴趣、概念、事件 | 项目、模块、技术栈、外部依赖、协作者 |
| observations 侧重 | **价值观、人生观、态度**的流露与判断 | **代码水平、数学水平、工程判断、项目偏好**的表现 |
| 常驻注入 | 价值观与人生观 + 沟通风格 | 能力画像 + 项目偏好 + 当前项目的时间线尾段 |
| 提炼侧重 | 价值判断、态度转变、关系变化 | 能力表现、技术决策、**改了什么代码** |
| dream 侧重 | 画像演进、价值观变化 | 时间线归并、能力画像更新、决策归档 |

**模板存在 `sections.yaml` 里，用户可改 —— 换模板不算改代码。**

**注意全局层（`shared/`）与项目分区是两套模板**：前者跨项目（身份、准则、能力画像、项目偏好），
后者按项目（项目目标、架构、决策、待办、时间线）。它们的 `sections.yaml` 各自独立。

> v9 修订：能力画像 / 项目偏好 / 技术栈偏好从原 `project/_shared` 移入全局层的
> `sections.yaml`（order 40/50/60）。聊天与项目分家的那部分（价值观/态度 vs 项目目标/架构）
> 保持不变 —— 用户明确要求"分成聊天记忆和项目记忆，两个记不一样的东西"。

### 4.2.6 项目时间线：摘要常驻 + 指针，详情按需取（v8 重写）

**需求原话**：「这个代码改动不是有钩子吗？能不能在 dream 的时候只整理大致内容，
然后后面附加个每轮钩子的链接？等 AI 意识到哪一轮对后面有影响之后再去仔细看改动内容」。

#### 4.2.6.1 好消息：diff 本来就挂在钩子上

本机核实 `dsh-tool-fs` 的类型声明 —— `write` / `edit` 会给自己的 `tool/result`
附加一个私有 `meta` 载荷：

```ts
/** write/edit 的私有 tool/result meta：已应用的上下文 diff 分块 */
export type FsDiffMeta = { diffs: FileDiff[] };

export interface FileDiff {
  path: string;
  oldText: string | null;   // 新文件 / 覆盖时为 null
  newText: string;          // 改动后内容
}
export declare const DIFF_CONTEXT = 3;   // 每个 hunk 前后各 3 行上下文
```

注释明确写着：该 meta **以 `unknown` 附加在 tool result 上，并随会话日志持久化**
（"persisted with the session log — it must be JSON-serializable"）。

**结论：「改了什么」不需要我们自己算 diff，原生已经算好并挂在钩子上了。**

**回退路径**：该 meta 是 dsh-tool-fs 的私有形状（"The producing tool owns and narrows
this opaque shape"），有随版本变动的风险。取不到时回退 `exec.arguments` ——
`ToolExecutionInput.arguments` 是"无损 JSON 可序列化的已解析参数"，
`write` 带 `content`、`edit` 带 `old_string`/`new_string`。
**信息一样够，只是少了 3 行上下文。**

#### 4.2.6.2 两层结构：摘要常驻，详情按需

```
tools/result  (exec + result)
   │ 取 result.meta.diffs；取不到则回退 exec.arguments
   ▼
raw/timeline/<date>.jsonl        【详情层】逐条完整记录
   { id, ts, tool, path, session, turn, cwd, hunks: FileDiff[] }
   │ dream 归并 —— 只写粗粒度摘要，不带代码
   ▼
sections/timeline.md             【摘要层】人类可读，每条带指针
   ### 2026-09-10
   - 改 src/db.ts 的索引重建逻辑 [→ t-20260910-a3f2]
   - 新增 src/timeline.ts          [→ t-20260910-b7c1]
   │
   │ AI 判断"这一轮对后面有影响"时才取详情
   ▼
memory_diff(id) 工具              【按需读取】返回该条完整 hunks
```

**为什么这样分**：

| | 摘要层 `sections/timeline.md` | 详情层 `raw/timeline/` |
|---|---|---|
| 内容 | 每条一行，只写"做了什么" | 完整 `FileDiff[]`（含 old/new/上下文行） |
| 注入 | ✅ **常驻注入**（体积小） | ❌ **永不主动注入** |
| 读取 | 每次会话自动 | 仅当 AI 调 `memory_diff(id)` |

- 摘要常驻 → AI 知道"什么时候改了什么"
- 详情不常驻 → **代码 diff 进上下文非常贵，且多数时候用不上**
- **取详情的触发权交给 AI**：它读摘要时发现"那次改动可能影响现在这个问题"，才去取

#### 4.2.6.3 已实现版本（P4.5）与上面设计的差异

上面的结构照做了；以下四处实现时改了，理由记在这里，**不同意可以直接推翻**：

| # | 设计写的 | 实现成 | 为什么 |
|---|---|---|---|
| 1 | 详情存 `raw/timeline/<date>.jsonl`，一条一记录 | `raw/timeline/<锚点id>.md`，**一轮一个文件** | 指针要能 O(1) 定位。jsonl 得先扫全文件才知道 id 在哪；一 id 一文件天然 1:1。复用 `anchors.ts` 那张 ids 表，也就兑现了「三处共用同一指针机制」那条洞察。markdown 而非 JSON，是为了保住 vault「可读、可手改、可 git」 |
| 2 | 指针形如 `[→ t-20260910-b7c1]` | `[→ 12]`，**与来源锚点共用同一套数字 id** | 两套 id 空间迟早会串。`[^N]`（断言）与 `[→N]`（时间线）由**同一个解析器**处理（`anchors.ts`） |
| 3 | 摘要由 **dream 归并**时写 | **轮次结束时即时写**一行 | ① dream（P6）还没实现，等它等于现在什么都没有；② §铁律要求"出窗口的轮次不许静默丢弃"，即时写才能保证覆盖；③ dream 仍可继续**重写/合并且润色** `timeline.md` —— 那是叠加，不冲突 |
| 4 | 回退 `exec.arguments`（`write` 的 `content` 等） | 只对**改动类工具**（write/edit/move/delete…）记一条"调用记录"，**不含 shell** | 收 shell 会让时间线变成命令流水账，把常驻注入的预算挤爆。**已知边界：命令行间接改的文件不会被采集** |

另外，摘要粒度是**一轮一行**而不是一改一行 —— 摘要要常驻注入，
一场重构按一改一行能写下几十行，那就违背了"不烧上下文"这个前提。
dream 阶段可以把它改写成人话（"重构了索引重建逻辑"），那才是摘要该有的样子。

对应实现：`src/timeline.ts`（采集 + 渲染）、`src/anchors.ts`（指针表）、
`src/markdown.ts`（按日期分组）、`mem_diff` 工具（`src/tools.ts`）。

#### 4.2.6.3 保留与兜底

- 详情层默认保留 **90 天**，之后只留摘要
- **diff 的权威副本仍在会话日志里**（原生持久化）—— 必要时可回捞，这是最后兜底
- 不 diff 文件系统：那要文件快照 + 全量比对，成本高、要额外存储；
  而"经手的改动"插件免费就能看到，覆盖度也够（代码都是通过工具改的）

**与 deliverables 的分工**：`dsh-client-ui-deliverables` 管"这一轮产出了哪些文件"（当轮 UI 展示），
我们管"这段时间改了什么"（长期记忆）。两者不冲突。

### 4.2.7 会话如何选空间

**★ 2026-09-14 改判（用户提出）：用 agent preset 定空间，不再从 cwd 猜。**

用户原话：「怎么隔开聊天和项目，觉得在**这里新增一个聊天 agent** 最对味儿，
因为本来聊天就是要自定义 agent 的，**别的就默认走项目**，除非用户主动提，
AI 可以主动查询另一个空间的记忆」。

**本机查证结果（非推测）—— 两件事都能做**：

| 问题 | 结论 | 依据 |
|---|---|---|
| 插件读不读得到当前会话用的是哪个 preset？ | ✅ **能** | `agentPreset` 是 DSH 的 **Session 投影**：`dsh-agent-presets` 导出 `agentPresetProjectionDefinition`（key=`agentPreset`，值 `string \| null`）。来源是创建时的 header 加空白期改选的 `agent-preset/selected` 事件；官方文档明确「重建要读投影，**不能只看 header**」 |
| 能不能加一个 preset？ | ✅ **能**，两条路 | ① `<dshHome>/.agent-presets/<id>/`（`USER_PRESET_DIR`，trust=`user`）——「Discovery re-reads the roots on every call」，所以**运行中新建即可见、不用重启**；② profile 里给 `dsh-agent-presets` 配 `config.roots` 加一个 root（可指向 dsh-mem 包内，随包发布） |

一个 preset = **一个目录**：`preset.yml`（显示名 / 描述 / order）+ **`agent.cordis.yml`（agent 的插件组合）**。
**目录名就是 preset id** —— 所以判定要按 id（如 `chat`），**不能按显示名**（`preset.yml` 里的 name 只是给人看的）。

**改判后的判定**：

```
会话启动 → 读 agentPreset 投影（每轮读，不缓存）
  ├─ id === 'chat'（自建的聊天 preset） → 读写 spaces/chat/（聊天记忆）
  └─ 其它任何 preset                     → 项目空间：按 cwd 推导分区
       （一个 preset 覆盖所有项目，"是哪个项目"仍由 cwd 决定 → projects/<项目名>/）
无论哪条路，全局层 shared/ 都注入。
跨空间：用户主动提 → 允许；AI 也可主动 `mem_search` 另一个空间（§4.2.4）
```

**降级路径**：读不到 `agentPreset`（投影为空 / 服务未就绪）时**回退到原来的 cwd 判定**
（登记表 > 仓库标记 > default）—— 那段逻辑先留着，等 preset 路径真机跑稳再删。

**这一步省掉了什么（信息架构从紧）**：

| 原机制 | 改判后 |
|---|---|
| `workspaces.yaml` 里"这目录算聊天还是项目"的登记 | **退役** —— 用户已经用 preset 显式声明了，不该再登记一遍 |
| `default: ask` + 「未登记工作区问一次」+ `state.json.asked` | **退役** —— 不再猜，也就不需要问 |
| 仓库标记（默认 `.git`）用来判"是不是项目" | 降级为**只在项目侧定分区**，不再用于判空间 |

**要小心的三点**：

1. **每轮读，不要缓存** —— 会话在空白期可以改选 preset（`agent-preset/selected` 事件会记），
   缓存一次会一直错。
2. **`sessionProjections` 是可选服务** —— 按本项目那条老坑处理（`subagents` / `webServer`
   都是并发启动、晚就绪，只 `get` 一次会拿到 `undefined` 并**静默失效**）：要重试，
   拿不到时明确降级，别静默。
3. **聊天 preset 的组成要定** —— 是"标准模式全套 + 一个标记"，还是"真的只有聊天能力"
   （不给编码工具）？用户说「本来聊天就是要自定义 agent」，所以后者才是终态；
   但**先按前者跑通**（改动最小），能力裁剪是后一步。

改类型（记忆空间 UI 里改）：**迁移而不合并** —— 原空间内容整体移入新空间的

## 5. 核心机制（自写）

### 5.1 写入：**对话中几乎不写，交给 dream**

> **v11 重写**。用户拍板：「**不要在对话过程中频繁改动 memory**，这个工具
> 除非用户要求改或者记忆跟之前的有冲突才能碰，**不然都由 dream agent 完成**」。
> 于是 §5.1 从"三轮提炼"缩成"一个提醒 + 一条采集"。

挂 `agent/turn-stopping`，只做两件事，**都不调模型**：

**① 「用户要求记住」的提醒**（`installAutoWrite`）
判定通过时 steer 一条带 `[mem-reflect]` 标记的消息，提醒模型落库。

**触发只有一个**：用户明说「记住 / 别忘了 / 以后都…」（只扫 `source.kind === 'user'`）。
~~连续工具调用 ≥N~~ 与 ~~距上次提炼 ≥N 轮~~ 两个轮次级触发**已删除** ——
那正是"在对话过程中频繁改记忆"的来源。（连跨轮计数器 `turnsSinceReflect` 也一并删了，
免得日后有人把"每隔 N 轮记一笔"加回来。）

**抑制**（任一即不触发）：子代理会话 / 本轮已反思过（防连环）/ 本轮最后一个工具就是写记忆的。

steer 的消息：

```
[mem-reflect] 用户这一轮要求记住东西（或者你自己说了要记住）。
① 用户明确要求记住的 → mem_remember（常驻记忆）
② 与已有记忆冲突的 → 以用户当下所说为准，改正
③ 其它一切 → 不要写。留给晚上跑的 dream。
```

**② 原始轮次采集**（`installTurnCapture`）
把这一轮的对话原文**追加**进 `raw/turns/<会话>.jsonl` ——
没有 LLM、没有 steer、不做判断，纯粹存素材。

**为什么必须有它**：把判断全推给 dream 是可以的，但**素材不能丢**。
没有这层，dream 晚上跑的时候就无米下锅。（它放在 `raw/` 下、不参与注入与检索排序，
因为它是**原始素材不是记忆**。）

**每条写入必须带来源锚点**（`session_id` + `turn_seq`），**否则拒绝入库** ——
没有锚点的记忆在 §5.5 的引用体系里是断链的。锚点由工具从 `exec.agent`
（`session.header.id` + 最后一个 `turn/start` 的 `turn`）自动取，**不是模型填的**；
取不到就拒绝写入。实现见 `src/anchors.ts` / `src/observations.ts` / `src/reflect.ts`。

**写入落点**（P4 已实现的部分）：由 cwd 经 `projectRootMarkers` 硬推导 ——
命中仓库标记 → 该仓库的分区；否则聊天空间。`mem_observe` **没有"选空间"的参数**，
所以调用方没有机会写错地方。`workspaces.yaml` 显式登记与"未登记时询问"仍留在 P4.6。

### 5.2 检索（主路径不需要向量）

1. A 层指令全量常驻
2. `sections/` 中标记常驻的（如个人背景、工作状态）全量常驻
3. **实体名精确命中**：从用户消息抽实体名 → 查 `idx_entries.name` → 读该页 + 顺一跳邻居
4. 未命中且实体页 > 200：向量粗筛 top-20 → LLM 重排 top-3
5. `observations.md` **不常驻**，仅在第 4 步检索命中时按需读取

分词用 CJK bigram + Unicode 整词（`[实测]` 这是中文检索正解，绕开 FTS5 分词坑）。

**聊天原文（RCC）不在这条链路上** —— 它是独立的一条召回，见 §5.8。

### 5.3 晋升与降级（三层之间的流动，dream 时执行）

**晋升** raw → observations：提炼轮写入时即时发生
**晋升** observations → sections/entities：满足任一
- 与已有确证记忆一致（corroborate）且再次出现
- 用户明确要求
- importance 判定高

**降级/清理**：
- observations 超过保留期（默认 30 天）且未被 corroborate → 归档到 `raw/archive/`
- sections/entities 中被 §5.4 冲突规则取代的 → 标 superseded，正文移入 `raw/superseded/`

### 5.4 冲突规则（[Kimi参考]）

**"新的赢"**：
- 旧档案 vs 新对话冲突 → 以新为准，旧条目写 `superseded_by` 并移出 canonical
- 档案 vs 用户**当下所说**冲突 → **以当下为准**，dream 时修正档案
- 检索时排除 superseded 条目

### 5.5 来源锚点与可见引用（[Kimi参考]）

Kimi 的 README / sections / entities 里**每条断言都带角标**（¹ ² ³ ¹² ²⁵）。
这不是装饰，是**可验证性**：读者能顺着角标回到来源轮次。

我们要做的：

2. 文件尾部或旁挂 `anchors` 表存 `[^12] → {session_id, turn_seq}`
3. (P9) 支持"锚点重访"：拿锚点重建当时的上下文再问一次，

### 5.6 dream（整理逻辑自写）

#### 5.6.1 调度：**统一晚上跑一次**（用户拍板 2026-09-11）

**用户原话**：「180 分钟一次改成**统一晚上处理**」。

所以**不用** meow 那套"空闲 180min 触发"——改成**每晚固定时间跑一次**：

| 项 | 值 | 说明 |
| --- | --- | --- |
| `dreamAt` | `03:00`（**待确认**） | 每晚到点检查一次，不是到点必跑 |
| `dreamIdleMinutes` | 15 | 到点时若最近 15 分钟还有会话活动，**推迟**到下一个整点再看 |
| 每日一次 | 是 | 跑过就在 `state.json` 记当天日期，同一天不再跑 |
| 无素材就跳过 | 是 | 先算"哪些会话有新轮次未整理"，一个都没有就**直接结束**，不烧钱 |
| DB 租约 | 保留 | 防重复跑；error 时**释放租约重试**而不是封存 |
| 子代理会话 | 不参与 | dream 自己的子 agent 产生的会话，绝不进素材 |

峰时抑制（09-12 / 14-18）就没必要了 —— 凌晨跑本来就不撞用户使用时段。

#### 5.6.2 结构：**两段式 + 每个会话派两个子 agent**（用户拍板 2026-09-11）

**用户原话（先）**：「需要多派几个子 agent，一般一个对话派一个，
而不是一股脑全让一个整理，当然要考虑到先后问题别让俩 agent 冲突了」。
**用户原话（后，修正）**：「**一个对话派两个 agent**，这样项目文件夹里有闲聊的东西
也可以归进闲聊区了，甚至用户价值观、用词、情绪什么的也可以从项目过程体现，
就是要跟 agent 说好了**项目的事儿少管，完全没有不写都行**」。

**为什么从"一个"变成"两个"**：归属不能靠文件夹（DSH 不支持给项目文件夹打 tag），
只能靠**内容判断**。所以按会话切根本切不出空间来 —— 一个会话里可能**同时**有
闲聊和项目内容。改成**每个会话派两个 agent，各捞各的**：

```
阶段 A（并行 · 只读）
   会话 1: [闲聊 agent] [项目 agent]
   会话 2: [闲聊 agent] [项目 agent]
   ...
   它们读**同一份**未归属素材，只吐 JSON，**不写任何文件**
        │  等全部收齐（barrier）
        ▼
阶段 B（串行 · 唯一写者）  汇总 agent，按 JSON 里的 space 归拢落库
```

**两条边界要写死在提示词里**（用户特别强调）：
- **闲聊 agent**：项目的事**少管**；但项目过程里露出的**用词/情绪/价值观**是它的。
  **一条都没有就返回空数组** —— 空是正常结果，不是失败。
- **项目 agent**：不碰价值观/情绪/用词；只捞目标/架构/决策/踩坑/待办/改动归并/能力信号。

#### 5.6.2.1 素材必须**未归属**地攒着

原始轮次落在 **`<home>/.dsh-mem/raw/turns/<会话>.jsonl`** ——
`shared/` 与 `spaces/` **之外**，既不是全局记忆也不是某个空间的记忆。

**为什么不按 cwd 分到各 vault 的 `raw/` 下**：那样等于**替 agent 把归属判完了**，
两个 agent 里项目那个就读不到"在项目目录里说的闲聊"。

### 5.8 聊天原文召回（RCC + 补丁 · 追加式）

**需求（用户原话）**：「其实我想保留聊天原文来着，检索匹配高的原文注入上下文，
**只保留用户的不保留 AI 的**」。形态由用户给出：「平时用一模一样的 RCC，
遇到语义特别接近的对话，并且检测到 RCC 中对应原文有 TLDR 截断，
就把这一段在 RCC 中完整显示，别的不动」。最后拍板**追加式**：
「直接追加带补丁版本，不就多了俩原文吗不打紧」。

**适用范围：只用于聊天空间（用户拍板 2026-09-14）** —— 「这个 RCC 只适合在聊天里面用，
在项目里面用感觉画蛇添足」。三条理由：

1. **项目空间已经有同一模式的对应物。** `sections/timeline.md`（摘要常驻 + `[→id]` 指针）
   + `raw/timeline/`（详情永不主动注入）+ `mem_diff(id)` 按需取（§4.2.6）。
   RCC + 补丁本质上是**同一个「摘要常驻、详情按需」模式**搬到聊天原文上 ——
   项目里再挂一套，就是两套并存、同一个问题两个答案。
2. **RCC 补的是"没有结构的东西"。** 聊天记忆是散的态度、生活、情绪，没有天然结构，
   所以要靠"最近 40 场用户原话"兜底；项目有结构（文件、diff、时间线），不需要兜底。
3. **★ RCC 按时间窗口取场，与项目的硬隔离直接冲突。** 「最近 40 场」是按会话**时序**切的，
   会把**别的项目**、甚至纯闲聊的场一起卷进来 —— 而 §4.2.3 定的是项目**硬隔离分区**。
   这一条是硬的：不是"值不值得"，是"跟已有铁律打架"。

**覆盖范围就是"时间上最近的 40 场"，不按空间筛**（用户 2026-09-14）：
「这 40 场就是时间最近的 40 场啊，这个没问题」。

- 时间窗口本身就是一个**自然的边界**，再叠一层"这一场算聊天还是项目"的判定，
  就是多开一个没有行为差别的抽屉（信息架构从紧：每一层都得挣得自己的位置）。
  **所以 `sessions` 不需要归属列。**
- 而且 RCC 装的是**用户说过的话**，不是**项目的内容** —— 跟项目记忆是两类东西。
  同一句话在哪个目录说的，跟它有没有用没有必然关系
  （在项目会话里同样可能说了关于自己的事）。
- 「只在聊天空间**注入**」（上面那条）与「哪些场进 RCC」是两件事，别混：
  前者是注入侧的范围，后者就是纯时序。

**RCC 是什么**：最近 **N 场会话**（默认 **20**，计数单位是**场**不是消息）里**用户的全部发言**，
逐字引用、不加摘要、不做检索。场与场之间、场内的发言之间用 `||||` 分隔。
场编号形如 `27. 0903T20:10 Claude误会`（日期+时间+场标题）。

**取数源**：`turns` 表（§4.1 的建表设计）—— `user_text` 与 `ai_compact` **分列存放**，
天然满足"只留用户的话"。**硬约束：两者永远不许合并成一个字段** ——
一旦合并，"只留用户"这条就永久做不到了。

**索引三层，别混**（用户指正 2026-09-14）：「关键词匹配索引的应该是**消息原文**，
然后对应到 RCC 里看看有没有被截断，所以**消息原文和对话都要索引**」。
我原先写的"零索引"是指**不再额外建倒排/向量索引** —— 措辞不严谨。
真正要的是下面三层各司其职：

| 层 | 表 | 单位 | 谁用 |
|---|---|---|---|
| 记忆 | `idx_entries`（**已实现**） | 一个 vault 文件 | §5.2 记忆检索 / `mem_search` |
| **消息原文** | **`turns`**（§4.1 已设计，**尚未实现**） | **一轮**（`user_text` / `ai_compact` 分列） | **RCC 的关键词匹配面** |
| **对话（场）** | **`sessions`**（§4.1 新增） | **一场**（`session_id` + 标题 + `in_rcc` + `rcc_truncated`） | RCC 的场编排与截断判定 |

**不建的东西**：倒排索引、向量索引、切块。**建的是表，不是检索引擎** ——
BM25 在这两张表上现算（这个量级毫秒级）；量级上去了再说，
那时也才有数据说该不该上索引。

**"被截断"必须是可查的状态，不能每轮重算**：RCC 是按 token 裁中段的，
重算既贵又不保证同结果。做法照抄 §5.7 的既有模式 ——
**拼 RCC 时把裁断结果反向回写进表**（那儿的 `turns.covered_by` 就是这么写的）：
`sessions.in_rcc`（在不在 RCC 内）+ `sessions.rcc_truncated`（这一场有没有被裁）。

**触发（每轮之前 · 宿主侧 · 全自动，不交给模型判断）**：

```
1. query = 本轮用户消息
2. 挑出 query 里**有辨识度的词**（不是 `记忆`/`这个` 这种满库都有的泛词）——
   一个都没有 → 本轮不补，连榜都不排
3. BM25 over turns.user_text —— 限定在 RCC 覆盖的那 40 场 → top-`rccPatchK`（默认 1）
4. 命中那一轮必须 ① 含有辨识度的词、② 在 RCC 里**看不见**（该场 rcc_truncated）
5. 本会话没补过**这一轮** → 取**那一轮的** user_text → 追加一段补丁
```

**全程三次查表，不扫文件、不读 MB 级原文** —— 原文只在第 5 步真要补时才读。

**RCC 本体形态**：`source.form = 'recall'` —— DSH 的定义原文：
*Material lifted out of another session's log, possibly reduced on the way in.*
（这套形式词汇表是**语义的、非视觉的**，见 `dsh-llm` 的 `ContextForm`。）

**补丁形态**：`source.form = 'notice'`（"一次性事件；它不取代任何东西"）。
正文**必须带场号 + 轮次**（`8. 0914T13:55 标题 · 第29轮`），
否则模型认不出它补的是哪一场的哪一句。一轮默认只补 1 段。

**去重账本（硬要求）**：`seen` 表，同一**轮**在同一会话里**只补一次**（键 = `会话id#轮次`）。
追加式不做去重就会累积 —— 用户连续三轮问同一件事，补丁就是三份。

**裁断标记必须显式**：被裁掉的中段要留 **`[TL;DR]`** 这类机器可识别的记号
（不能只用 `……` —— 模型分不清"这里省略了"和"用户真打了省略号"，
一旦分不清就不会去补，整条链路失效）。

**★ 标记本身不带"省了多少"（用户 2026-09-17 纠正）**：原话「这个**此处省略 xx 字**
不要放进去啊，**不更耗 token 了吗**」。标记自己就吃 token，而"省了多少"是**我们自己
算得出来的**（`droppedTurns` / `cutCount` 都记着），没必要每次注入都带上。
所以两层裁剪共用**同一个光秃秃的 `[TL;DR]`** —— 不再用「字 / 句」区分是哪一层裁的。

**★ 裁剪是两层（用户 2026-09-15 / 09-17 分次给的规格）**：

1. **单条发言**：保留头 **60 字** + 尾 **40 字**。
   用户原话：「**不是掐单场的中段，是掐用户单句话说的太长的中段**……按头 60 字尾 40 字算吧」。
   一场几十条发言，**整场**掐中段会把中间那几十条**整条丢掉**（连头尾都没了）；
   **逐条**掐则每条都留头留尾，丢掉的只是每条里最不重要的那截过程。
2. **整场**：只保留**前面 12 句**（`rccHeadTurns` 12 / `rccTailTurns` **0**），后面插一行标记。
   用户调研 Kimi 回来的结论：「它那边**不仅有**用户一条对话过长截断机制，**还有整场截断机制**，
   只保留 12 句剩下的全没了……**怪不得能保留 40 场**」。
   一开始抄成了"头 6 + 尾 6"，用户 2026-09-17 纠正：「**整场截断就保留前面 12 条啊，
   不是前 6 条后 6 条**」。**尾 0 是刻意的**：只有老场才会被裁，而老场的"结尾"往往
   只是寒暄，最不值钱；近场本来就整场完整带上。

**★ 两层都只留同一个 `[TL;DR]`，不标"省了多少"（用户 2026-09-17）** ——
理由见上（标记也吃 token，而省了多少我们自己算得出来）。

落点：`sessionUserText(turns, {head, tail, headTurns, tailTurns})`；
`sessions.rcc_truncated` = 「**这一场里有任一层被裁**」（补丁的判据靠它）。
取完整原文时传 `NO_CUT`（两层都关）。

**★ 与 Kimi 的关键差别：它砍掉就没了，我们砍掉能补回来。**
补丁取的是**命中那一轮**的完整原话 —— 用户 2026-09-17 看过实际注入后定死：
「**不是补整场对话啊，是触发关键词的那一个对话**」。此前实现成"该场完整原文"
（两层都不裁），实测一轮能端上来 2k+ 字符（那次 2 段共 4481 字符，而正文只是
28 字的一句话）—— 一句话的问题不该付一整场的 token。

**两道闸门（同一天加的）**：
1. **泛词不算命中**：一个词在语料里越普遍，越没有"把某一轮捞出来"的能力。
   阈值在真实库（223 轮）上量过：`这个` 35.0% / `记忆` 24.7% / `现在` 23.3% 是泛词，
   `rcc` 4.5% / `机票` 0% 才有辨识度；门槛取 `df ≥ 3 且 df/n ≥ 10%`。
   触发场景：用户一句「宝宝你有记忆了吗」，`记忆` 一个泛词就把两整场拉进了上下文。
2. **补的是那一轮、不是那一场**（见上）。去重键也随之从「场」变成「轮」(`会话id#轮次`)。
   上界：每轮最多 `rccPatchK`（默认 **1**）段 × 一轮原话的长度。

改完在真实库上复核：同一句话从 2 段 / 4481 字符 → **1 段 / 121 字符**；
单查「记忆」→ **0 段**。

**覆盖场数与成本（09-15 重算）**：整场压到 12 句后，一场 100 轮也只 ≈ 360 字
→ **40 场 ≈ 1.4 万字 ≈ 8–14k token**（之前按"不裁句数"算，40 场要 6 万字，所以才一度降到 20）。
量级落在用户认可的档位（「15-20k 可以接受，kimi 那个光上下文注入就要 40k 左右」，
**写进 README 即可**，不必改配置）。真机实测：29 场两层全开 = **6312 字符**
（只开单条截断是 14401）；真正被整场咬到的只有 5 场（30/39/39/63/40 句）。

**为什么选追加式，而不是"每轮重发 RCC、就地展开"**：**不赌 `snapshot` 的 supersede 语义。**
DSH 的 `form: 'snapshot'` 声明"后一条取代前一条"，但快照的**框架行**
（"这条快照取代先前的快照"）**本身是模型可见文本** ——
需要专门告诉模型这件事，恰恰说明旧的还在、需要它自己忽略。
追加式**不依赖这个未验证的平台行为**：不管 supersede 是真删还是软宣告，
追加式的行为与成本完全一样。（要验也不是不能验：发两条同源 snapshot，
比对第二次请求的消息体。但既然不依赖它，就不必先花这个成本。）

**成本上界（结构性，不是估算）**：补丁只能补 RCC 覆盖范围内（40 场）的场，
且每场只补一次 → **整会话最多 40 段，每段一次**。
最坏情况 = RCC 完全不截断，**不会比它更多**。

**已否决：原文切块 + 建索引 + 向量检索 + 注入片段。**
被这一版全面覆盖 —— 同一层需求（把用户原话放进上下文），
本形态更轻、作用域更小、且不引入向量依赖。
将来若真出现立项理由，条件写明：**RCC 的截断缺陷用"改截断策略"解决不了**，
且出现可复现的、落在 40 场之外或被截断处的漏召回实例。

**边界**：

| 情况 | 动作 |
|---|---|
| 命中，但 RCC 里未被截断 | **什么都不做**（它已完整在上下文里） |
| 命中，被截断，但截断处不含关键词所在段 | 仍补全文（不做精细定位，简单优先） |
| 会话首轮，RCC 尚未注入 | 不补 |
| 本轮已补过这一场 | 不补（`seen` 账本） |

**依赖的 DSH 能力**：会话标题（场编号需要，走 `dsh-session-title` 那套）；
上下文形式 `recall` / `notice`（`dsh-llm` 的 `ContextForm`）。

### 5.9 原文归档与按指针取回

**归档不在我们这儿，在 DSH 的会话日志里**（契约已核实）：

```
~/.dsh/sessions/<工作区>/<会话id>/session.v3.jsonl.zstd
```

append-only，且持久化层 README 明写「**Nothing deletes session files** … no deletion API」。

| 层 | 存什么 | 为什么它该存在 |
|---|---|---|
| **DSH 会话日志** | **完整原文**（含工具结果） | 官方保证只增不减 → **唯一归档** |
| `raw/turns/<会话>.jsonl` | 在线采集 `{session, turn, at, cwd, space, user, assistant, tools}` | **格式解耦**：日志有 v0→v1→v2→v3 迁移，格式会变；这是我们自己的稳定格式 |
| `turns` 表 | 派生索引 | 可从上面那层重建（删了不丢） |

**指针 = `(session, turn)`** —— 三层都有，天然对齐。但**取原文的入口还不存在**
（全库搜 `sessions/` / `.jsonl.zstd` / `zstd` **零命中**），所以现在这个指针是**断的**。
它同时是 §5.8 补丁链路第 4 步（"取该场全部 user_text"）与 §5.5「锚点重访」的落点。

**★ 实现约束（2026-09-15 实测）：DSH 日志是【多帧 zstd】。**
`zstdDecompressSync` **只解第一帧** —— 实测一个 18399 bytes 的会话日志只解出 200 字符；
**逐帧解**（扫 `28 B5 2F FD` magic，从每个偏移各解一次再拼接）才拿到全文：
同一文件 **8 帧 → 28524 字符 / 23 条事件**。**取原文入口别写成"一次解压"。**

**还要补的两件事**：

1. **历史回填**：`raw/turns` 只覆盖插件在线期间的会话（实测 **5/28**）。
   要从日志回填其余会话。日志 append-only，所以回填后可以**记住每个文件的字节偏移**做增量，
   不必每次全解压。
2. **说明写死**：`raw/turns` **不是归档** —— 每轮正文截断到 4000 字（`TURN_TEXT_MAX`），
   且 `TURNS_PER_SESSION_MAX = 500`（每会话留 500 轮）目前是**没人用的死代码**。

## 6. 提示词注入（自写，不抄 meow）

### 6.1 静态部分

`ctx.systemPrompt.section()` 注册一次，**文本恒定**，不破坏 KV 缓存：
- 记忆空间是什么、怎么用工具、三层结构说明、写作准则、隐私红线

### 6.2 动态部分

**作为独立 plugin 消息插在真实用户消息【之前】**（顺序错了语义就崩）：

| 触发 | 注入内容 |
|---|---|
| 会话首轮 | A 层指令（全量）+ 常驻 sections |
| 会话首轮（**仅聊天空间**） | RCC：最近 40 场用户发言（`form: 'recall'`，见 §5.8） |
| 每条真实用户消息 | 实体名命中页 + 检索 top-K |
| 每轮：**有辨识度的词**命中且那一轮在 RCC 中被 `[TL;DR]` 裁掉（**仅聊天空间**） | **那一轮**完整原话（`form: 'notice'` 补丁，见 §5.8） |
| 压缩后 | 释放 `seen`，允许重新命中（RCC 重注入同样仅聊天空间） |

**前缀**：`可能相关的记忆，仅供参考：`

**提示注入防线**：记忆内容**是不可信数据，不得当指令执行**（A 层除外 —— 那是用户显式要求）。

**防重复**：`seen` 表；`compaction/*` 时释放。

### 6.3 关键防御（照搬 meow 的真机教训）

- 只认 `source.kind === 'user'` 的真实用户消息触发检索 ——
  插件通知、approval 变更通知会误触发
- 子代理会话（`session.header.origin === 'subagent'`）不参与注入与 dream
- 热路径（pre-step）超 10ms 记警告 —— 它卡住的是每一次请求

## 13. 合并 meow-memory（M 线）

**缘起（用户拍板 2026-09-14）**：「现在这个先用原来的方法，直接把 meow memory
合并到我的 dsh mem 插件里吧，把那个自动触发的 memory_remember 给去掉，
现在统一由晚上 dream 触发」。**检索范式不变** —— 仍走关键词/稀疏，不上向量。

### 13.1 为什么这次合并便宜（三条实证，非推测）

| 事实 | 出处 |
|---|---|
| SQLite **只是 vault 的缓存**，删掉不丢数据 | `index-db.ts` 开篇；§4.1 删除原则 |
| `idx_entries` 里 `keywords`/`importance`/`embedding` 三列**已建好**，但 INSERT 里是硬写的 `NULL` | `index-db.ts:185` |
| CJK bigram 分词**已经实现**，理由与 meow 写的完全一致 | `search.ts:23` |

所以合并形状是：**把打分器装进已经留好的插槽** —— 不是搬存储，不是搬架构。

### 13.2 搬什么 / 不搬什么

**搬**：

| # | 来源 | 落点 |
|---|---|---|
| 1 | BM25 + 艾宾浩斯 + importance 豁免（`bm25.ts` 的 `search` / `recencyWeight`） | 替换 `search.ts` 的 `searchEntries` 打分器 |
| 2 | 每消息关键词命中注入（`inject.ts` 的 `buildHitInjection`） | §6.2 注入表「每条真实用户消息」行 |
| 3 | 压缩后重注入（`buildReinjection`） | §6.2「压缩后」行 |
| 4 | 会话级 seen 记账（injected / searched / accessed / written） | `seen` 表（§4.1 已设计） |

**不搬**：7 层 SQLite 表结构、空闲 180min 的 dream 调度（本方案是统一晚上）、
自动反思触发（M0 已关）、embedding 那一路（用户拍板不上）。

### 13.3 打分器规格（照抄 `bm25.ts`）

```
score(t,d) = idf(t) * tf*(k1+1) / ( tf + k1*(1 - b + b*len/avgdl) )
idf(t)     = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )
k1 = 1.5        b = 0.75

final = raw * w
  w = 1                                  若 importance ≥ 3，或 raw ≥ 0.85 × 本轮最高 raw
  w = recencyWeight(now - updated_at)    否则

recencyWeight（按天）：<1→1.0  <2→0.9  <4→0.8  <7→0.65  <15→0.5
                       <30→0.35  <60→0.25  <180→0.15  ≥180→0.08
```

**两个消费方、两个匹配面**（meow 的真机教训，必须照搬）：

| 消费方 | 匹配面 | 理由 |
|---|---|---|
| `mem_search`（AI 主动深挖 · 宽召回） | `name + rel + body`（全文） | 查询是模型写的词，要召回优先 |
| 每轮关键词命中（窄触发 · top-2） | **`keywords`** | 全文匹配噪音大 —— 常见 bigram（"的时"）每条消息都有，长条目一碰词就整条注入 |

### 13.4 front-matter 字段清单（M 线的核心交付）

§5.4 的 `superseded_by` 与「检索时排除 superseded 条目」都要求**逐条元数据持久**；
而 `rebuildVault` **已经在读** front-matter 的 `attrs.status`（`index-db.ts:206`）。
所以「逐条元数据走 front-matter」是**既定实现，不是选择题**。本清单把它定死：

| 字段 | 类型 | 谁写 | 何时写 | 缺失时 |
|---|---|---|---|---|
| `status` | `active \| stale \| archived \| superseded` | dream | 确证 / 归档 / 被取代 | 视为 `active` |
| `keywords` | `string[]` | dream | 写正文时顺手写 | 回退 `body` 前 100 字（§13.3 的匹配面） |
| `importance` | `int 1–4` | dream | 同上 | 视为 `2`（不触发衰减豁免） |
| `superseded_by` | `string`（取代者的 rel 路径） | dream | §5.4 冲突规则命中时 | 无 |
| `anchors` | `int[]` | **工具**（§5.5：不是模型填的） | 写入时 | 无 |
| `updated_at` | ISO 时间 | 工具 | 每次写入 | 回退文件 `mtime` |

**`keywords` 是稀疏路的燃料** —— 它是 LLM 在写入时"先把话说全"的产物。
匹配面用它而不是正文，正是这个方案能不用向量的前提。

### 13.5 分期（**不与既有 P 序列混编号** —— P1 已被「vault 读写 + UI」占用）

| 期 | 内容 | 前置 | 验收 |
|---|---|---|---|
| **M0** | 关 meow-memory 的自动反思（`cordis.patch.yml` 加 `reflect: false`） | 无 | ✅ 已完成（重启 profile 生效） |
| **M0.5** | **最小对照集**（10–20 条真实 query，baseline = 现有打分器） | 无 | 有可量化基线；**库里只有几十个文件，此刻是做它最便宜的时候** |
| **M1** | front-matter 字段落地 + `index-db` 填 `keywords`/`importance` + 换打分器 | M0.5 | 测评集上**不劣于** baseline |
| **M2** | 注入链路：关键词命中 + 压缩重注入 + `seen` 账本 | M1 | 每轮能召回 |
| **M3** | 数据迁移（120 条：user 3 / rules 6 / project 35 / fact 25 / lesson 49 / topic 2） | M1 | 条目都在 vault 里 |
| **M4** | 下线 meow-memory：停注入 → 停工具 → 卸载 | M2、M3 | 只剩一套系统 |

**为什么 M0.5 是硬前置**：换打分器等于一次性引入四个新权重
（idf / 长度归一化 / 时间衰减 / importance 豁免）。`search.ts` 自己的注释写着
「等 P-1 的检索测评集做出来，该调的权重拿数据说话，**而不是凭感觉先调一轮**」——
没有基线，就没法说这次换是变好还是变坏。这也与「先跑 spike 再定设计」同一条经验。

**规模上不必做大**：现在 vault 里只有几十个文件，**此刻是写对照集最便宜的时候**；
等库大了反而写不动。所以 M0.5 只要求 10–20 条真实 query，不是大测评集。

**meow 那边没有现成的测评集可拿（已核实）**：它的 `tests/` 只有 5 个**客户端 UI 测试**
（delegate-notice / vanish / dream-icon / dream-skip / fold），`scripts/` 全是构建与诊断脚本
（check-fixes / check-lang / diag-dream / hash-check / locate-load / mtime-check / stat-lib …），
全库搜「命中率 / 召回 / 测评集」只命中两处**文案**（CHANGELOG 与 settings-page 的 hint）。
**它的检索质量从来没被量化过** —— 也是靠 smoke + 真机踩坑修补出来的。

**所以"照抄 ≠ 直接可用"，三条**：

1. **索引单位不同。** meow 的 doc = 一条记忆（短、有 title 与 keywords）；
   dsh-mem 的 doc = 一个**文件**（`sections/*.md` 可能几千字）。
   长度分布差一个量级，而 BM25 的 `b=0.75`（长度归一化强度）与 `recencyWeight`
   的分桶，都是对某种长度分布与更新频率的**假设** —— 换语料就得重看。
   这正是「先验证规模前提」那条经验的同一形状。
2. **M1 同时改了写入侧。** `keywords` 现在硬写 `NULL`，M1 要让 dream 把它写进
   front-matter。只换函数是换算法，改写入是改行为，两者叠加。
3. **meow 的检索没被测过**（见上），所以"它已经在真机上验证过"这个前提本身不成立。

**若最终仍决定不做对照集**：那就必须把 M1 的验收标准从「检索**不劣于** baseline」
改成「跑通 + smoke 绿」—— **可以省掉证据，但不能省掉证据还声称有证据。**

**M3 的唯一难点**：归属映射。meow 的 `project` 是自由字符串
（`dsh-memory-plugin` / `全局`），而 vault 分区是按 cwd 推导的**目录名**
（`MemoryChat` / `dsh-mem`…）—— 就是 P4.6 偏离表里那个"同一项目多套名字"的坑。
映射表要先定死，否则 35 条 project 记忆不知道往哪落。

**M1 是性价比最高的一期**：只动派生索引与打分器，**不碰注入** ——
跑坏了也不影响日常对话，且 `mem_search` 立刻变好。

## 附：P4.6 实现与设计文档的偏离

| # | 设计写的 | 实现成 | 为什么 |
|---|---|---|---|
| 1 | mem 根下中心化的 `projects.yaml`（key → path/name/last_seen） | **每个分区自带 `meta.yaml`** | 分区被搬走/备份/复制时元信息跟着走；不会出现"注册表说有、目录却不在"的两边不一致。少一个会失同步的文件就少一类 bug |
| 2 | 工作区类型页有**类型下拉**（可直接改） | **只读展示** + 给出登记表文件路径 | 与常驻记忆同一条原则：写入口收敛成工具（`mem_space`），UI 只负责看得见。手改文件本来就是"可手改"设计的一部分 |
| 3 | `memory_search` 跨项目检索 | 工具名 `mem_search` | 命名空间与参考实现错开（`mem_*` vs `memory_*`），两个插件可共存 |
| 4 | （未明确）未登记工作区"ask"之后怎么办 | 问过就写 `<home>/.dsh-mem/state.json`，**不再反复问**；回答前按聊天空间兜底 | 每会话都问一遍等于每次都在念同一句话，用户会直接关掉插件。兜底选聊天空间是因为它破坏性最小：记散一点 vs 把内容关进用户不知道的分区 |
| 5 | （未明确）索引条目主键 | `space:project:rel` **复合键** | 原用 vault 内相对路径，实测"2 个 vault × 2 个同名文件"插 4 条只剩 2 行 —— 跨项目检索会读到被静默覆盖的数据 |

**另外两处实现选择**：① 跨项目检索**每次先重建索引再查** —— vault 是事实源、索引只是缓存，
而用户随时可能手改文件；与其维护增量失效逻辑，不如每次重建（这个量级重建比维护便宜）。
② `mem_space set` 为项目时**立刻把分区建出来** —— 登记是明确动作，用户期待"登完就能看到它"。
